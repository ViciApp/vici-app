# Internationalisation (i18n)

This page is the contract for **any user-visible string** added or
changed in the frontend. If you're not sure whether something needs to
go through `t(...)`, the default answer is yes.

> Sibling pages: [`a11y.md`](./a11y.md) (semantics, ARIA, contrast),
> [`reusability.md`](./reusability.md) (where shared things live),
> [`structure.md`](./structure.md) (folder taxonomy).

## TL;DR

```svelte
<script lang="ts">
	import { localeStore } from '#lib/stores/locale.store.ts';
	import { t } from '#lib/utils/i18n.utils.ts';
</script>

<h1>{t({ locale: $localeStore, key: 'markets.page.title' })}</h1>

<p>{t({ locale: $localeStore, key: 'markets.page.sub' })}</p>
```

- **Never** put a raw English string inside a `.svelte` template.
- **Always** add the new key to **every** locale catalog under
  `src/lib/constants/messages/`: not just `en.ts`.
- Interpolation uses `{name}` placeholders; pass them via `params`.
- Brand / token names (`Vici`, `Bitcoin`, `BTC`, `ICP`, `ckUSDC`,
  `VXP`, `Internet Computer`, …) and version strings (`v0.0.7`) are exempt;
  they don't translate. The `local-rules/no-bare-svelte-text` rule has
  a built-in allowlist for these tokens (see `BRAND_TOKENS` in
  `local-rules/no-bare-svelte-text.cjs`); update both the rule and the
  list below when adding a new brand.

## Adding a new string: the checklist

1. **Pick a key.** Namespace it by feature: `markets.empty`,
   `wallet.send.cta`, `flow.streak.broken`, `a11y.close_dialog`.
   Use `snake_case` inside dotted segments. Reuse an existing key if
   the literal is already in `en.ts`; duplicates make catalogs heavier
   and translators noisier.
2. **Add the key to every `live` catalog** under
   `src/lib/constants/messages/`: `en.ts`, `it.ts`, `es.ts`, `de.ts`,
   `fr.ts`, `pt.ts`, `zh-Hans.ts`.
   - English is the source of truth: write it first.
   - For the other six, write a real translation. Don't paste English.
     If you genuinely can't translate one, leave it out of that catalog
     only; the runtime falls back to `en`. **But CI will flag this for a
     `live` locale** (see `npm run check:i18n`), so prefer adding all
     seven. `soon` locales (registered in `LOCALE_REGISTRY` but not yet
     translated) have no catalog and resolve to English via their
     fallback chain; they are not checked for missing keys.
3. **Wire the component:**

   ```svelte
   <script lang="ts">
   	import { localeStore } from '#lib/stores/locale.store.ts';
   	import { t } from '#lib/utils/i18n.utils.ts';
   </script>

   <button>
   	{t({ locale: $localeStore, key: 'wallet.send.cta' })}
   </button>
   ```

4. **Interpolation:** put `{placeholder}` in the catalog string and pass
   `params`:
   ```ts
   t({
   	locale: $localeStore,
   	key: 'a11y.page_n',
   	params: { page: currentPage }
   });
   ```
   Don't build sentences with `+`. Don't ship two half-keys and glue
   them together; grammar varies per locale.
5. **Run the gates:**
   ```bash
   npm run check:i18n   # catalog alignment
   npm run lint         # eslint (incl. no-bare-svelte-text)
   npm run check        # svelte-check
   ```

## What gets translated

| Surface                                     | Translate?                                                                                                      |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Text inside `.svelte` templates             | **Yes.**                                                                                                        |
| `aria-label`, `alt`, `title`, `placeholder` | **Yes**: they're user-visible / read by AT.                                                                     |
| Toast / notification copy                   | **Yes.**                                                                                                        |
| Form error / validation copy                | **Yes.**                                                                                                        |
| Empty state copy                            | **Yes.**                                                                                                        |
| Brand / token names                         | No (`Vici`, `BTC`, `ICP`, `ckUSDC`, `VXP`, …).                                                                  |
| Code identifiers, URLs, CSS variables       | No.                                                                                                             |
| `console.error` / log messages              | No, engineer-facing.                                                                                            |
| Admin console copy                          | **Yes**, unless the surface is explicitly noted as operator-only in `design.md`. The default is "translate it". |

## How the active locale is resolved

`localeStore` seeds itself once, at module load, with a single rule:

1. **A stored choice always wins.** If `LOCALE_STORAGE_KEY`
   (`vici.locale.v1`) holds a value, the store boots with it and never
   re-detects.
2. **Otherwise we catch the device language.**
   `detectBrowserLocale()` matches `navigator.languages` /
   `navigator.language` in two tiers: an exact tag wins against **any**
   registered locale, `live` or `soon` (so a `pt-BR` browser seeds
   `pt-BR`, an `es-MX` browser seeds `es-MX`); a primary-subtag fallback
   is then scoped to `SUPPORTED_LOCALES` only (`pt-PT` / `pt` → `pt`,
   `de-DE` → `de`), falling back to `en`. That catch is then
   **persisted**, so it becomes the durable default and later visits
   resolve straight from storage.

The language picker writes through `localeStore.set(...)`, which
overwrites that value, so an explicit choice is respected from then on.
There is no separate "has chosen" flag; the presence of the storage key
is the signal. The inline boot script in
[`app.html`](../../../src/app.html) applies the same precedence
(saved → device → `en`) before first paint, purely to get
`<html lang>` / `dir` / `[data-locale]` right; the store re-resolves
authoritatively after hydrate.

## Locales on the satellite wire

Several `AppLocale` ids contain a hyphen (`zh-Hans`, `pt-BR`, `es-419`,
…), which would break the Sputnik code generator if leaked into a
`j.enum([...])` schema. So the `locale` field stays `j.string()` in
[`market-translation.schema.ts`](../../../src/lib/schema/market-translation.schema.ts),
and the satellite service validates the incoming value against
`SUPPORTED_LOCALES` (derived from `LOCALE_REGISTRY`) at write time; see
`src/satellite/services/market-translation.services.ts`.

## CI / local enforcement

- `npm run check:i18n`: drives strictness from each locale's `tier` in
  `LOCALE_REGISTRY`. `live` catalogs must exist and expose the **same key
  set** as `en.ts` (missing or extra keys fail). `soon` locales may be
  absent or partial (they fall back to English) and are only flagged for
  keys not present in `en`. Failures exit non-zero.
- `npm run lint`: runs ESLint, including
  `local-rules/no-bare-svelte-text`. The rule activates per file: it
  only fires when the file already imports `#lib/utils/i18n.utils.ts`,
  meaning the component has _opted into_ translation. This keeps the
  signal high while we pay down the long tail of untranslated
  components.
- Both run in `.github/workflows/checks.yml` via the `lint` job
  (`check:i18n` is invoked by `lint`).

## Common mistakes

- **Calling `t()` outside `$:` / `$derived` / a `.svelte` template**:
  `$localeStore` isn't reactive in plain `.ts` modules. If a `*.utils.ts`
  or `*.services.ts` truly needs a translated string (e.g. a toast),
  accept `locale: AppLocale` as a parameter and let the caller pass
  `get(localeStore)` from `#lib/stores/locale.store.ts`.
- **Adding a key only to `en.ts`.** CI will block you. Add it to all
  seven `live` catalogs in the same PR.
- **Changing an existing string's value in `en.ts` only.** `check:i18n`
  compares key _sets_, never values, so stale wording in another catalog
  ships green. Grep the key across every file in
  `src/lib/constants/messages/`: `pt-BR` is `tier: 'soon'` but carries an
  almost complete catalog, while `es-419` / `es-MX` / `es-AR` / `ja` carry
  only `welcome.*`.
- **Translating brand names or code identifiers.** Don't.
- **Disabling `local-rules/no-bare-svelte-text` with an inline
  comment.** Translate the string instead. A genuine exemption (e.g. a
  literal ticker symbol) is rare enough to deserve a comment explaining
  _why_ the disable is correct.

## The locale registry

`LOCALE_REGISTRY` in
[`locale.constants.ts`](../../../src/lib/constants/locale.constants.ts)
is the single source of truth for every locale the app knows about. Each
entry carries its `id`, native `label`, English `name`, picker `short`,
`region` / `regionLabel` / `flag` (for a region-aware picker), an ordered
`fallback` chain ending at `en`, optional `base` / `hidden` flags for a
language's neutral dictionary, and a `tier`:

- `live`: catalog is populated and kept fully aligned to `en`.
- `soon`: registered for detection and fallback, but the catalog is
  absent or partial; missing keys resolve to English via `fallback`.

`SUPPORTED_LOCALES` (the flat `{ id, label, short }` list the picker
iterates today) is derived from the registry as the visible `live`
locales. `t()` resolves a key by walking `localeFallbackChain(locale)`,
so a `soon` locale always renders real English copy rather than a raw
key.

### Promoting a `soon` locale to `live`

1. Create `src/lib/constants/messages/<locale>.ts` with the same keys as
   `en.ts`.
2. Register the catalog in `src/lib/utils/i18n.utils.ts`.
3. Flip the entry's `tier` to `'live'` in `LOCALE_REGISTRY`.
4. Run `npm run check:i18n` until it's green.
