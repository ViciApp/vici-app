# Satellite Structure & Naming

## Layout

```
src/satellite/
├── index.ts                    Top-level wire-up: single file
├── api-schemas.ts              Generated by `juno functions build` (do not hand-edit)
├── satellite.did               Generated Candid (do not hand-edit)
├── satellite_extension.did     Generated Candid (do not hand-edit)
├── tsconfig.json               Satellite-only TS config
├── services/                   One <area>.services.ts per concern (`ls` for all ~45), e.g.:
│   ├── engine-sync.services.ts     Mirrors Juno roles → icdc-core Vici engine
│   ├── leaderboard.services.ts     Server-side leaderboard reads
│   ├── market-metadata.services.ts Creator/admin market context updates
│   ├── profile.services.ts         Profile validation + lookups
│   ├── referral.services.ts        Referral code assignment, redemption + VXP payout
│   ├── relation.services.ts        Friend / follow primitives
│   ├── roles.services.ts           Role doc validation
│   ├── vxp-onboarding.services.ts  VXP onboarding hooks
│   └── vxp-payout.services.ts      Shared VXP ledger transfer
└── utils/                          Catalog: reusability.md
    ├── candid.utils.ts             IDL types off the generated factories
    ├── logger.utils.ts             Structured logging wrapper
    ├── regex.utils.ts              escapeRegex
    ├── vxp-payout.utils.ts         VXP transfer error mapping
    └── wire-format.utils.ts        camelCase wire schemas + toWire / fromWire
```

## What goes where

| Concern                                               | File                                                                                                                                           |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Query handler** (read-only over canister state)     | A function exported from `services/<area>.services.ts`, wired via `defineQuery` in `index.ts`.                                                 |
| **Update handler** (mutates state, returns to caller) | A function exported from `services/<area>.services.ts`, wired via `defineUpdate` in `index.ts`.                                                |
| **`onSetDoc` hook** (post-write trigger)              | A function exported from `services/<area>.services.ts`, registered via the `setDocCollections` map in `index.ts`.                              |
| **`onDeleteDoc` hook** (post-delete trigger)          | Same shape, via the `deleteDocCollections` map in `index.ts`.                                                                                  |
| **`assertSetDoc` assertion** (pre-write veto)         | Same shape, via the `assertSetDocCollections` map in `index.ts`.                                                                               |
| **Cross-canister call** (registry / clearing)         | Co-located with the hook that needs it (e.g. `engine-sync.services.ts` calls the registry).                                                    |
| **Pure helper**                                       | `utils/<name>.utils.ts`.                                                                                                                       |
| **Schema**                                            | Reuse `#lib/schema/*.schema.ts` whenever the same shape is consumed by the FE; only declare a satellite-only schema if the FE doesn't need it. |
| **Constants**                                         | Reuse `#lib/constants/*.constants.ts` (path is symmetric; the satellite imports them via the same alias).                                      |

`index.ts` is intentionally a **declaration file**; it should only:

1. Import handlers from `services/`.
2. Wire them via `defineQuery` / `defineUpdate` / `defineHook` /
   `defineAssert`.
3. Map collection → handler so each `onSetDoc` / `onDeleteDoc` /
   `assertSetDoc` call dispatches to the right service.

If `index.ts` starts to grow logic, push it down into `services/`.

## Naming conventions

Same suffix system as the frontend:

| Suffix          | Meaning                                           | Example                   |
| --------------- | ------------------------------------------------- | ------------------------- |
| `*.services.ts` | Handler module (queries, updates, hooks, asserts) | `engine-sync.services.ts` |
| `*.utils.ts`    | Pure helpers, no I/O                              | `logger.utils.ts`         |

Casing: `kebab-case` filenames, `camelCase` exports, `PascalCase` types.

## Imports

Use the `#lib`, `#satellite`, `#declarations` and `#root` subpath imports
from [`package.json`](../../../package.json) `imports`. Each is mirrored in the
satellite [`tsconfig.json`](../../../src/satellite/tsconfig.json) `paths`,
which `scripts/satellite-upgrade-needed.mjs` reads to walk the import graph:
a subpath import missing there is treated as an npm package and silently
skipped.

```ts
import { Collection } from '#lib/constants/collections.constants.ts';
import { UserProfileSchema } from '#lib/schema/profile.schema.ts';
import { syncRoleToEngineOnSet } from '#satellite/services/engine-sync.services.ts';
```

The local rule `local-rules/no-relative-imports` is `error` under `src/`,
which includes the satellite. Don't reach for `../` to cross folder
boundaries.

**Direction.** The satellite imports from `#lib` only what runs without a
DOM: constants, schemas, types and pure utils (`collections.constants.ts`,
`canisters.constants.ts`, `#lib/schema/*`, `types/vxp-award.ts`, ...).
The frontend imports from `#satellite` only the `fromWire*` converters in
`utils/wire-format.utils.ts` (profile, leaderboard, referral and
market-translation services). Nothing else crosses in either direction.

## Forbidden imports

- **`@junobuild/core`.** That's the FE client. Satellite code uses
  `@junobuild/functions` instead.
- **Anything DOM-flavoured** (`document`, `window`, `localStorage`,
  Svelte components, browser-only utils). The satellite tsconfig keeps
  the `dom` lib for dependency typings, so the type check does not catch
  them: the rule is on you.
- **Hand-edits** to `api-schemas.ts`, `satellite.did`,
  `satellite_extension.did`: all generated by
  `npm run juno:functions:build`.

## Collections and `juno.config.ts`

Collection names are pinned in two places that must stay in sync:

- [`juno.config.ts`](../../../juno.config.ts): the deployment config
  that creates and configures the collection on the satellite.
- [`src/lib/constants/collections.constants.ts`](../../../src/lib/constants/collections.constants.ts):
  the typed `Collection` enum the satellite + FE both import.

When adding a new collection, update both files in the same PR. The
satellite's `setDocCollections` / `deleteDocCollections` /
`assertSetDocCollections` arrays use the typed enum, so a missing entry
becomes a TS error at the dispatch table.

**Storage (binary asset) collections are separate.** They live under
`satellite.collections.storage` in `juno.config.ts`, NOT the
`datastore` array, and they are NOT part of the `Collection` enum
(that enum is Datastore-only). Their names live where they're used
(e.g. `LEAGUE_IMAGES_COLLECTION` in `#lib/types/league.ts`). The FE
uploads to them via `#lib/services/storage.services.ts` and persists only
the returned download URL on the owning Datastore doc; never a base64
data URL.

## Where to put new code (decision tree)

1. **Is it a hook / assertion / endpoint?** → pick the matching service
   file under `services/`. If none fits and the concern is genuinely new,
   add `services/<area>.services.ts` and wire it from `index.ts`.
2. **Is it a pure helper?** → `utils/<name>.utils.ts`.
3. **Is it a schema shared with the FE?** → `#lib/schema/<area>.schema.ts`,
   imported from the satellite.
4. **Is it generated?** → don't create it by hand. Run
   `npm run juno:functions:build`.
5. **None of the above?** → ask. Don't invent a folder.
